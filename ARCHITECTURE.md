# grapesjs-pages — архитектура и путь к CMS

## Как устроено сейчас

```
plugin.ts ── связка: опции → store → менеджер → UI → команды/клавиши
│
├─ store/            PageStore (интерфейс) ← IndexedDbPageStore | MemoryPageStore | свой
├─ core/
│   ├─ PagesManager  CRUD, загрузка страницы в редактор, автосохранение, undo/redo
│   └─ SnapshotHistory  стек снимков одной страницы (чистый класс)
├─ clipboard/        копирование компонентов со стилями между страницами
├─ sync/
│   ├─ RestClient    HTTP по openapi.yaml, If-Match, HttpError
│   ├─ plan.ts       buildPlan(locals, listing) — чистая функция, вся логика решений
│   └─ SyncService   настройки сервера, plan() / apply()
├─ ui/               Sidebar, диалоги, поиск панели/контейнера, CSS
└─ i18n/             23 локали, editor.I18n под `pagesManager.*`
```

Правило: ядро (`core`, `sync`, `store`, `clipboard`) не трогает DOM сайдбара.
UI подписан на события `EVENTS.*` редактора и сам перерисовывается. Поэтому
другой UI (React-панель, вкладка в сайдбаре sidebar-tools, CMS-админка) можно
повесить на те же события, не меняя ядро.

Модель данных: **страница = целый проект GrapesJS** (`getProjectData()`), у
каждой свои стили и ассеты. Переключение = `loadProjectData()`.

## Исправлено при переносе

1. **Двойная вставка по Ctrl+V.** GrapesJS добавляет стандартные клавиши
   (`Keymaps.onLoad`) уже после плагинов, поэтому `km.remove('core:copy')`
   из оригинала тут же отменялся: срабатывали обе вставки, а Ctrl+Y для
   повтора пропадал. Клавиши теперь настраиваются в `onReady`.
2. **Потеря последней правки при быстром переключении страницы.** `flush()`
   сохранял только при взведённом таймере автосохранения, а часть изменений
   GrapesJS сообщает асинхронно. Теперь `flush()` всегда сверяет состояние со
   снимком.
3. **Порча моделей при копировании.** `toJSON()` в GrapesJS неглубокий, и
   оригинал записывал `attributes` прямо в живые модели дочерних компонентов.
   Теперь работаем с глубокой копией. Явный `id` ставится только там, где на
   него ссылается CSS или он уже был, поэтому вставленный HTML не обрастает
   лишними `id`.
4. **Наложение панелей.** Если «Страницы» открывались командой, а preset
   открывал Style Manager (preset-webpage делает это при выделении), были
   видны обе панели. Кнопка теперь `listen: true`.
5. **Работа после `editor.destroy()`.** GrapesJS 0.21 не шлёт `destroy`:
   таймеры и `beforeunload` продолжали дёргать мёртвый редактор. Добавлена
   проверка `isEditorAlive`.
6. Мелочи: `renderList()` без `catch` (необработанные промисы), версии
   сравниваются как строки (`1` и `"1"`), `onupgradeneeded` не падает на
   существующих хранилищах, повторное подключение плагина не дублирует UI,
   клавиатурная навигация по списку, перевод на 23 языка вместо жёсткого русского.

## Предложения: путь к CMS

Ниже — по порядку окупаемости. Первые три меняют модель данных, их лучше
решить до того, как появятся реальные сайты с данными.

### 1. Разделить «сайт» и «страницу» — главное решение

Сейчас у каждой страницы свой CSS, свои ассеты и своя копия шапки и подвала.
Для CMS это означает: правка меню — N правок, общий стиль кнопок копируется,
ассеты дублируются.

Предлагаемая модель:

```
Site   { id, name, globalCss, assets[], symbols[] (шапка/подвал),
         settings (домен, языки, шрифты), version }
Page   { id, siteId, slug, title, parentId, order,
         status: draft|published, seo { title, description, og… },
         content: { components, pageCss }, layoutId?, version }
Layout { id, siteId, content }   // шаблон со «слотом» под контент страницы
```

При открытии страницы в редактор грузится `globalCss + layout + content`.
При сохранении проект разбирается обратно: стили с селекторами страницы — в
`pageCss`, остальное — в `globalCss`. Нативные Symbols GrapesJS (0.21+)
закрывают шапку и подвал «правка в одном месте».

Альтернатива — нативные Pages GrapesJS (`editor.Pages`): одна модель со
всеми страницами. Для 5–10 страниц это проще, но сайт грузится целиком и
стили смешиваются, поэтому для CMS я бы не брал.

Совместимость: `PageRecord.data` остаётся как «legacy-страница»; миграция в
`content` пишется один раз.

### 2. Сервер — источник истины, IndexedDB — черновики и офлайн

Сейчас всё наоборот: локальная база главная, сервер — ручная синхронизация.
Для CMS с несколькими редакторами нужен `RemotePageStore` (тот же интерфейс
`PageStore`): чтение и запись идут сразу на сервер с `If-Match`, IndexedDB
остаётся кешем и очередью неотправленного. Ручной диалог синхронизации
остаётся для офлайн-режима. Интерфейс уже позволяет это без изменений ядра.

### 3. Публикация отдельно от сохранения

`draft` и `published`: «Опубликовать» отправляет на сервер не только
`ProjectData`, но и готовые `html` и `css` (`editor.getHtml/getCss`), чтобы
сайт отдавался без GrapesJS. Плюс ревизии (`/pages/{id}/revisions`) для
отката. В контракт (`openapi.yaml`) добавить `POST /pages/{id}/publish`.

### 4. Дерево и адреса страниц

`slug` + `parentId` + `order` → дерево в сайдбаре (drag-n-drop), уникальность
`slug` проверяется на сервере, `title`/SEO-поля редактируются в свойствах
страницы (можно отдать вкладкой в grapesjs-sidebar-tools).

### 5. Несколько вкладок и несколько людей

Сейчас две вкладки браузера с одной страницей молча перезаписывают друг друга.

- `BroadcastChannel` — оповещать другие вкладки о сохранении, чтобы они
  перечитывали страницу или показывали «изменено в другой вкладке».
- Web Locks API — «страница открыта в другой вкладке», только чтение.
- На сервере — мягкая блокировка («редактирует Иван») поверх `If-Match`.

### 6. Память истории

Undo хранит до 50 полных снимков проекта на страницу. Для больших страниц
это десятки мегабайт. Варианты: лимит по байтам вместо количества, сжатие
(`CompressionStream`), хранение диффов (JSON Patch) или undo только для
активной страницы со сбросом остальных.

### 7. Безопасность

Bearer-токен лежит в IndexedDB открытым текстом и доступен любому скрипту на
странице. Для CMS лучше сессия на httpOnly-cookie (тогда `token` не нужен, а
CSRF-заголовок передаётся через опцию `headers`) или короткоживущий токен с
обновлением. Сервер обязан санитизировать `ProjectData` перед публикацией,
потому что в нём может быть произвольный HTML и `<script>`.

### 8. Ассеты

Ассеты сейчас внутри проекта страницы (часто как data-URL). Для CMS их нужно
вынести в общую медиатеку сайта: grapesjs-cloud-assets уже даёт UI и
провайдеры, нужен только серверный провайдер «медиатека CMS».

### 9. Мелкое, но полезное

- Поиск и фильтр страниц, когда их больше 20.
- Своё окно переименования и подтверждения вместо `window.prompt/confirm`
  (они блокируют поток и плохо выглядят).
- Пункт «Копировать на страницу…» в grapesjs-context-menu через
  `pages-manager:copy` и `api.open()`.
- Экспорт и импорт всего сайта в ZIP или JSON (бэкап IndexedDB).

## Предлагаемый порядок

1. Утвердить модель Site/Page/Layout (п.1) и контракт API v2.
2. Эталонный сервер (Node, как `box-token-server` у cloud-assets) по контракту.
3. `RemotePageStore` и публикация (п.2–3).
4. Дерево страниц и SEO (п.4), затем вкладки и блокировки (п.5).
